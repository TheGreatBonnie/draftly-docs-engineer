# PR Event Workflow: Per-run SSE + Hybrid RQ + Frontend Live-UI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make PR runs visible and streamable (per-run SSE), durably dispatched (hybrid RQ/in-process) exactly like onboarding initialization runs, **and live in the frontend** — wire the `/workflows/[id]` detail page, the reviews detail, **and the workflows list page** to live backend data (Tasks 4 + 6–10).

**Architecture:** The GitHub webhook creates a jobs row + SSE ticket for the run and **registers a `github_workflows` row** (PR identity: owner/repo/issue_number/title/actor/run_id), then dispatches to a single registered task handler — via RQ when enabled, else the in-process worker (same handler, mirroring onboarding). The PR workflow function becomes publisher-capable so graph stream envelopes + terminal `workflow_result` reach `GET /workflows/{run_id}/events`, and updates the job status to `running`/`completed`/`failed`. `github_workflows` is the **PR-identity store** (`owner/repo/issue_number/title/actor`) — it carries the fields `jobs`/`workflow_events` lack (PR title, actor, sourceLabel) and joins to them via `run_id`. Task 4 adds a `GET /workflows` list endpoint over this join so the workflows **list** page is live; the detail page remains SSE-driven.

**Tech Stack:**
- **Backend:** Python 3.11, FastAPI, RQ (redis-py), Redis streams, `sse-starlette`, pytest + pytest-asyncio, `unittest.mock`.
- **Frontend:** Next.js 16 (App Router), React 19, SWR, lucide-react, Tailwind v4, `@testing-library/react` + Vitest, ESLint (next). Verification: `npm run lint`, `npm run test` (Vitest), `npm run build` (runs `tsc`).

## Global Constraints

- Only **merged** PR events (`event_type == "pull_request.merged"`) proceed; non-merged PR actions are skipped **before** any jobs row/ticket/enqueue (preserve existing skip semantics — no job created for a skip).
- Mirror onboarding's exact patterns: `jobs.upsert_on_conflict`, `_tickets(request).issue(...)`, `enqueue_job` RQ branch + in-process `worker.run_task` fallback guarded by `rq_enabled and rq_queues and task_handlers`.
- Job-status updates are **best-effort** (never fail the workflow); jobs-row creation failure in the webhook is **fatal** (500).
- `github_workflows` registration in the webhook is **best-effort** (never fail the workflow), matching job-status updates — a failure to write the PR-identity row must not abort the run already in flight; only the `jobs` row + ticket are fatal.
- Do **not** write a `github_workflows` row for skipped (non-merged) PRs or non-PR events — only the merged-PR path registers one (mirror the jobs-row rule).
- Keep `github_workflows.workflow_id` unique as the idempotency key (`ON CONFLICT (workflow_id)`), and set `workflow_id = event_id` so it joins to `jobs.run_id` / `workflow_events.run_id`.
- Do **not** emit dashboard lifecycle events (`job_started`/`job_completed`/`run_completed`) — out of scope.
- Do **not** invent onboarding-style stage envelopes (`stage_manifest`/`stage_progress`/`overall_progress`); use the graph's native stream envelopes.
- All source files must pass `ruff check`; tests run with `pytest` via `draftly-agent-backend/.venv/bin/python -m pytest` (or `.venv/bin/python -m pytest` if venv at repo root).
- `ctx.repositories` is the composition-wired repositories bundle (has `.jobs`); `context.publisher` is the `_TeePublisher` when streaming is enabled, else `None`.

Runs the graph via a **publisher-capable** runner (so `_invoke_streaming` emits graph envelopes + terminal `workflow_result` when `context.publisher` is set), and flips the job status to `"running"` / `"completed"` / `"failed"`. Terminal `completed` maps only from `DELIVERED`; `FAILED` maps to `failed`; `SKIPPED`/`DUPLICATE`/`PENDING_REVIEW` leave the row as `pending`/`running` (best-effort, never `completed`).

**Why (two runner construction sites — do not regress):** There are two places that build `WorkflowRunner`. The composed runner in `app/composition/workflows.py:163` already passes `publisher=publisher` (used by the webhook's direct `app_state.workflows.runner.run` call). But this task handler (`github_pr_workflow.py`) is the **second construction site**, and it is the path used once RQ/in-process dispatch (Tasks 1–3) lands — so it is the one that actually needs the publisher. The rewrite **must** construct `WorkflowRunner(context, publisher=context.publisher)` (NOT the current bare `WorkflowRunner(context)`). If this line is left as `WorkflowRunner(context)`, the per-run SSE replay store (`workflow_events`) will stay empty on the in-process/RQ path even when streaming is enabled, and `GET /workflows/{run_id}/events` will return no events for merged-PR runs. Mirror this exact `publisher=context.publisher` shape (it matches the existing support workflows, e.g. `discord_support_workflow.py:21`).

```python
"""GitHub pull-request workflow (plan §7.2).

Thin adapter: normalized PR event → WorkflowRunner (documentation graph).
The runner owns idempotency, graph build, invocation, and outcomes.
When context.publisher is set, the runner streams graph envelopes and a
terminal workflow_result over the per-run channel. Job status is mirrored
to the jobs table (running/completed/failed) so the run is visible to
/workflows/{run_id}/events.
"""

from __future__ import annotations

from typing import Any

import structlog

from draftly.workflows.context import WorkflowContext
from draftly.workflows.runner import WorkflowRunner
from draftly.workflows.state import WorkflowState, WorkflowStatus

logger = structlog.get_logger(__name__)


def _resolve_run_id(event: dict[str, Any], run_id: str | None) -> str:
    return run_id or str(event.get("event_id") or "")


async def _set_job_status(context: WorkflowContext, run_id: str, status: str) -> None:
    """Best-effort: persist job status; never fails the workflow."""
    jobs = getattr(getattr(context, "repositories", None), "jobs", None)
    if jobs is None or not run_id:
        return
    try:
        await jobs.update_status(job_id=run_id, status=status)
    except Exception:
        logger.warning("pr_job_status_failed run=%s status=%s", run_id, status)


async def run_pull_request_workflow(
    context: WorkflowContext,
    event: dict[str, Any],
    run_id: str | None = None,
) -> WorkflowState:
    """Run the documentation graph for one pull-request event."""
    run_id = _resolve_run_id(event, run_id)
    await _set_job_status(context, run_id, "running")

    runner = WorkflowRunner(context, publisher=context.publisher)
    state = await runner.run(event)

    if state.status == WorkflowStatus.FAILED:
        await _set_job_status(context, run_id, "failed")
    elif state.status in (WorkflowStatus.SKIPPED, WorkflowStatus.DUPLICATE):
        # A skip/duplicate (e.g. non-merged PR replayed or idempotency duplicate)
        # is not an error; leave the row as pending/running rather than marking
        # completed/failed so /workflows/{run_id}/events replay stays coherent.
        pass
    elif state.status == WorkflowStatus.PENDING_REVIEW:
        # Intermediate — human review gate, not terminal completion.
        pass
    elif state.status == WorkflowStatus.DELIVERED:
        await _set_job_status(context, run_id, "completed")
    else:
        # Fallback for any future status: only DELIVERED is success, FAILED is
        # failure; other unknowns should not mark completed.
        logger.warning("pr_workflow_unknown_status run_id=%s status=%s", run_id, state.status)

    logger.info(
        "pr_workflow_done run_id=%s status=%s",
        state.run_id,
        state.status.value,
    )
    return state
```

## Frontend Architecture & Data Contracts (Tasks 6–10)

**Assumes backend deliverables exist:** the merged-PR webhook creates a jobs row (`run_id = event_id`) + SSE ticket **and a `github_workflows` PR-identity row** (`title`, `owner`/`repo`/`issue_number`, `actor`, `run_id`) — Task 4. The PR runner streams native Strands envelopes (`node_start`, `tool_progress`, `node_stop`, `handoff`, `workflow_result`) plus a terminal `workflow_result`/summary, and (Task 10) `store_interrupt` persists a structured `reason` dict + `GET /reviews/{review_id}` returns it, and `GET /reviews/by-run/{run_id}` + a `pr` identity block are available.

- **Live list endpoint (Task 4):** `GET /workflows` → `{ items: [{ run_id, title, target_doc, trigger_label, status, current_stage, stages: string[], current_stage_color, time }] }`. `target_doc` is `null` today; `stages` follows the real graph node order. Task 7 consumes this.
- Per-run SSE hook: `draftly-agent-frontend/hooks/use-workflow-events.ts` — `useWorkflowEvents(run_id)` already connects to `GET /workflows/{run_id}/events`, auto-fetches a single-use ticket via `POST /workflows/{run_id}/stream-ticket`, dedups by `seq`, and derives:
  - `status` (`idle|connecting|live|closed|error`), `events: StreamEvent[]`, `nodeStates: Record<node_id, "running"|"completed"|"failed">`, `text`, `reason`.
- Native event types the hook already handles (`use-workflow-events.ts:6-16`): `node_start`, `node_stop`, `handoff`, `text_delta`, `tool_progress`, `stage_change`, `stage_manifest`, `stage_progress`, `overall_progress`, `workflow_result`. The backend emits the graph-native subset: `node_start`, `tool_progress`, `node_stop`, `handoff`, `workflow_result` (+ any terminal summary event agreed in Task 2).
- **The real Strands documentation graph node ids** (`draftly-agent-backend/src/draftly/orchestration/graphs/documentation_graph.py:152-193`) are:
  `classify → context → research → impact → {answer | update | create} → evaluate ⇄(revise)→ deliver`
